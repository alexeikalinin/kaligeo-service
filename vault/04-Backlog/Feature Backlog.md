### Alisa (Яндекс Алиса) / YandexGPT — сетевая недоступность из-за границы
**Статус:** ⚠️ код реализован, но **ни разу не отвечал** — 0 успешных `QueryResult` за всю историю проекта
**Приоритет:** P1
**Дата диагностики:** 2026-09-23

**Проблема (диагностировано, не догадка):**
`llm.api.cloud.yandex.net` (Yandex Cloud Foundation Models API — на нём построены и YandexGPT, и Алиса) блокирует/роняет запросы с иностранных IP. Подтверждено несколькими независимыми способами:
- Ключ и `YANDEX_FOLDER_ID` реальные (вытащены из Vercel Production) — платформа даёт `configured: true`, но любой запрос падает с `fetch failed` / `ConnectTimeoutError`.
- Даже голый `GET` без ключа и без тела на `https://llm.api.cloud.yandex.net/` — таймаут 8 сек, то есть блок на сетевом уровне, раньше авторизации.
- В БД — 0 строк `QueryResult` с `platform IN (YANDEXGPT, ALISA)` за всю историю проекта, включая прошлые локальные тесты и прод.
- Ключевое наблюдение пользователя: **без VPN сайт открывается, с зарубежным VPN — нет**. Значит блокировка идёт по гео/принадлежности IP, не по коду/антивирусу.
- Для сравнения — в проекте Kalinin DA другие Yandex-продукты работают без проблем: `api.direct.yandex.com` (Direct), `api-metrika.yandex.net` (Metrika), `api.datalens.tech` (DataLens). Это рекламные/аналитические API, которым нужен международный доступ (рекламодатели по всему миру) — поэтому они открыты. `llm.api.cloud.yandex.net` — это Yandex **Cloud** (вычислительная платформа, аналог AWS/GCP), у неё, судя по всему, гео-фильтрация по IP на уровне комплаенса.
- Из этого следует: и Vercel, и Trigger.dev (оба почти наверняка в US/EU дата-центрах) — тоже иностранные IP для Yandex. Значит проблема не только в локальной разработке, а и в бою.

**Что нужно, чтобы починить:** запросы к `llm.api.cloud.yandex.net` должны физически идти с российского (или как минимум не заблокированного Yandex Cloud) IP. Прямой правкой кода это не решить — нужен сетевой релей. Детали реализации → [[#YandexGPT — план релея через российский IP]]

### Рекомендуемый вариант: авто-скан после заявки

**Флоу:**
1. Клиент заполняет форму на лендинге → `POST /api/contact`
2. Сервер сразу запускает `FreemiumScan` по домену из поля "сайт"
3. Через ~10-15 мин клиент получает email: "Ваш AI-отчёт готов" + ссылка на `/preview/{scanId}`
4. Страница preview показывает частичные данные (3-4 платформы, без PDF, без action plan)
5. CTA: "Разблокировать полный отчёт" → страница выбора тарифа → оплата → полный аудит

**Почему это работает лучше чем просто письмо:**
- Клиент видит реальные данные по своему бизнесу — не абстрактное обещание
- Создаёт FOMO: видит что данные есть, но часть скрыта
- Нет ручного шага от администратора для первого касания
- Время до ценности: 15 мин вместо "несколько часов"

**Технически уже есть:**
- `FreemiumScan` модель в БД
- `/api/freemium/scan` — запускает скан
- `/preview/{scanId}` — страница с результатами
- Нужно только: вызвать freemium-скан из `/api/contact` + доработать email с результатами

**Альтернативный вариант (проще):** сразу после заявки отправлять demo-отчёт (`/report/demo`) с именем клиента, без реального скана. Быстрее в реализации, но менее персонализировано.

## YandexGPT — план релея через российский IP

**Задача:** `lib/ai-clients/yandexgpt.ts` и `lib/ai-clients/alisa.ts` сейчас стучатся напрямую в `https://llm.api.cloud.yandex.net` — с иностранного IP (Vercel/Trigger.dev) это блокируется. Нужен промежуточный сервер с российским IP, который сам достучится до Yandex и вернёт ответ.

Оба клиента используют один и тот же API (`foundationModels/v1/completion`), разница только в `modelUri` (`yandexgpt/latest` vs `yandexgpt-lite/latest`) — значит и релей, и правки кода общие для обеих платформ.

### Шаг 0 — Дешёвая диагностика (15 мин, бесплатно) — сделать в первую очередь

Прежде чем платить за VPS, проверить дешёвый вариант:
1. В Yandex Cloud Console создать минимальную Cloud Function (Node.js), которая просто отвечает `200 OK`.
2. Дать ей публичный HTTP-триггер / повесить на API Gateway, получить публичный URL.
3. Дёрнуть этот URL с иностранного IP (можно попросить сделать это здесь же, в Claude Code, или через любой внешний curl-сервис).
4. **Если отвечает** — публичный ingress самого Yandex Cloud (Functions/API Gateway) не блокируется для иностранных IP, в отличие от `llm.api.cloud.yandex.net` → делаем **Вариант A (Cloud Function)**, он дешевле и без VPS.
5. **Если тоже не отвечает** — гео-блок общий для всего Yandex Cloud ingress → сразу делаем **Вариант B (VPS)**.

### Вариант A — Yandex Cloud Function как релей (если шаг 0 подтвердит доступность)

1. Установить `yc` CLI, авторизоваться тем же сервисным аккаунтом `kaligeo-sa`, что уже используется для `YANDEXGPT_API_KEY`.
2. Написать функцию (Node.js, ~30 строк): принимает `POST {prompt, systemPrompt, model: "yandexgpt"|"yandexgpt-lite"}`, проверяет заголовок `X-Relay-Secret`, изнутри Yandex Cloud вызывает `llm.api.cloud.yandex.net` (запрос уже внутри инфраструктуры Яндекса — блокировка не должна применяться), возвращает текст ответа.
3. Ключ и folder ID хранить как env-переменные самой функции (не светить наружу).
4. Задеплоить (`yc serverless function create` + `version create`), повесить HTTP-триггер или API Gateway, получить публичный URL вида `https://xxxxx.apigw.yandexcloud.net/relay`.
5. Добавить в Vercel + Trigger.dev env: `YANDEX_RELAY_URL`, `YANDEX_RELAY_SECRET` (через `/save-keys`, чтобы не потерять).
6. Переписать `yandexgpt.ts`/`alisa.ts`: вместо прямого fetch на Yandex — fetch на `YANDEX_RELAY_URL` с заголовком секрета.
7. `isConfigured()` обеих платформ — проверять наличие `YANDEX_RELAY_URL`/`YANDEX_RELAY_SECRET` вместо старых переменных (сами ключи Yandex переезжают внутрь функции).
8. Прогнать тот же smoke-тест «один вопрос платформе», что использовался при диагностике 2026-09-23.

**Оценка:** ~2-3 часа, стоимость — копейки (serverless, оплата за вызовы).

### Вариант B — VPS у российского хостера (если шаг 0 покажет блок и на Cloud Functions)

1. Арендовать VPS у российского провайдера (Timeweb Cloud, Selectel, REG.RU, Beget — любой с реальным российским IP), минимальные характеристики достаточны (1 vCPU/1GB), ~150-400₽/мес.
2. Поднять лёгкое приложение-релей (Node/Express или Fastify, один POST-эндпоинт) с тем же контрактом, что и в Варианте A: принимает запрос, проверяет секрет, форвардит в Yandex, возвращает ответ.
3. TLS — Caddy (автоматический Let's Encrypt) или nginx + certbot, поддомен вида `yandex-relay.kaligeo.ru` (один A-record на IP VPS).
4. Процесс-менеджер (`pm2` или systemd) для автоперезапуска.
5. Тот же набор правок кода, что в шагах 5-8 Варианта A (`YANDEX_RELAY_URL`/`YANDEX_RELAY_SECRET`, правки клиентов, smoke-тест).
6. Мониторинг: простой uptime-чек (UptimeRobot free tier) на publichealth-эндпоинт релея, чтобы узнать о падении VPS раньше, чем это всплывёт как «Yandex снова не отвечает».

**Оценка:** ~3-5 часов + ~150-400₽/мес постоянно.

### Общее для обоих вариантов
- Один и тот же контракт релея — можно начать с Варианта A и при необходимости позже перейти на B без изменения кода клиентов (только `YANDEX_RELAY_URL`).
- `Promise.allSettled` в `trigger/steps/execute-queries.ts` уже гарантирует, что падение релея не роняет весь аудит — просто YandexGPT/Алиса выпадут из отчёта как сейчас, деградация не хуже текущей.
- После починки — обновить `all_keys.md` (память) и эту запись в бэклоге, убрать статус ⚠️.
