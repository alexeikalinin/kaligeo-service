# KaliGEO — план предрелизного тестирования

Дата: 2026-10-09. Основан на маршрутах, тарифах и фоновых задачах текущего репозитория.
Это план будущих проверок, а не подтверждение работоспособности. Все пункты изначально НЕ ПРОВЕРЕНЫ.

## 1. Правила проведения и критерии релиза

**P0** — блокирует выпуск: потеря заявки/оплаты, чужие данные, неработающий основной путь, неверный рынок/валюта, отсутствие обещанного результата. **P1** — обязательно проверить до выпуска; дефект исправить либо явно убрать затронутую функцию из релиза и публичных обещаний. **P2** — удобство, дополнительные устройства и улучшения.

Для каждого пункта ниже вести результат: `ID | рынок | окружение/версия web и worker | данные | ожидаемое | фактическое | PASS/FAIL/BLOCKED/N/A | доказательство | дефект | дата/проверяющий`. N/A допустим только для функций, явно исключённых из релиза.

Доказательства: снимок экрана, реально полученное письмо и его заголовки, конечный URL после переходов, ID заявки/скана/аудита, ID фонового запуска, статус платежа, файл отчёта. Не сохранять секреты, полные платёжные реквизиты и действующие приватные ссылки в общедоступные материалы.

Условия выпуска:

- [ ] Все P0 пройдены на релизной версии для BY и RU; открытых P0 нет.
- [ ] Все заявленные функции P1 пройдены; исключения явно согласованы и отражены в интерфейсе/тарифах.
- [ ] Каждая продаваемая AI-платформа дала реальный ответ из рабочего окружения и попала в полный аудит. `configured: true` недостаточно.
- [ ] Все типы писем реально доставлены на контрольные ящики, все ссылки пройдены вручную до конечного действия.
- [ ] Длительные цепочки проверены ускоренно в изолированном окружении и контрольными запусками с настоящим расписанием. Незавершённые длинные прогоны явно отмечены.
- [ ] Оплата → запуск → готовый отчёт → письмо → доступ клиента пройдены без ручного исправления БД.
- [ ] Повторные события не создают повторных списаний, отчётов, рассылок или аудитов.
- [ ] Мониторинг сбоев, восстановление и откат проверены; после последнего исправления повторены затронутые сценарии и короткий релизный прогон.

## 5. Письма: доставка, содержание и полный путь

**Общий протокол для КАЖДОГО письма в таблице:**

1. Запустить реальное событие, получить ID отправки, проверить результат Resend и фактическое получение в ящике. API `success`/`sent` не равно delivered/inbox.
2. Проверить Inbox/Spam, задержку доставки, отсутствие дублей, корректную обработку bounced/blocked адресов и отказа провайдера. Отправка не должна считаться успешной при ошибке Resend.
3. Проверить From, display name KaliGEO, Reply-To и фактическую доставку ответа в нужный ящик. Проверить SPF/DKIM/DMARC и выравнивание домена по заголовкам; логотип/BIMI — если обещан.
4. Сверить имя, компанию, нишу, score, конкурентов, тариф, дату, валюту, сроки и язык с данными клиента. Нет `undefined`, пустых блоков, чужих данных и необоснованных фактических обещаний.
5. Открыть ВСЕ ссылки: CTA, текстовые, футер, домен, demo, preview, отчёт, PDF, login, unsubscribe, mailto. Записать конечный URL после всей цепочки редиректов и выполнить целевое действие.
6. Для BY конечные страницы/отправитель/оплата BY; для RU — RU. Проверить также ссылку из чужого браузера, без cookie и на телефоне.
7. Проверить отображение в Gmail/Яндекс/Mail.ru/корпоративной почте, mobile и dark mode, без картинок. Кнопки читаемы, письмо не обрезано, кириллица не испорчена.
8. Отписаться, дождаться следующего шага и доказать отсутствие маркетингового письма. Транзакционные сообщения после отписки должны следовать явно принятой политике.

- [ ] TIME-05 P0: повторная заявка, retry, перезапуск worker и деплой между письмами не теряют цепочку и не дублируют её.
- [ ] TIME-06 P1: ускоренный прогон меняет время только в изолированном тестовом режиме; настоящий прогон проверяет сохранение ожиданий после restart/deploy. Для SA-4 нужен контрольный 45-дневный прогон либо явный незакрытый пункт.

## 14. Порядок прогонов

1. **Инвентаризация:** окончательно зафиксировать продаваемые функции, тарифы, рынки, доступные AI и список писем; убрать устаревшие обещания. Для неподключённого GigaChat и неподтверждённого релея завести блокеры.
2. **Автоматические проверки:** существующие unit/integration, типы, линтер, build; добавить недостающее покрытие для рынка, доступа, callback/idempotency и цепочек. Проверки с mocks не считать доказательством работы внешних сервисов.
3. **Изолированное окружение:** негативные случаи, гонки, тарифные ограничения, ошибки провайдеров, ускоренные рассылки и расписания, sandbox оплаты.
4. **Реальные интеграции:** ответы всех AI из рабочих сред, Blob файлы, фактическая доставка каждого письма, все ссылки, контрольные production платежи.
5. **Полные конверсионные пути:** FLOW-01…12 для BY/RU с журналом переходов; desktop/mobile; без ручной помощи клиенту.
6. **Продолжительные проверки:** настоящие цепочки, restart/deploy между ожиданиями, период подписки, напоминания, 45-дневная ветка. Начать заранее, не в день выпуска.
7. **Нагрузка и восстановление:** согласованный объём, отказы, backup/restore, rollback.
8. **После исправлений:** каждый дефект воспроизвести до исправления и проверить после; повторить связанный сквозной путь.
9. **Релизный прогон после деплоя:** оба домена → заявка → письмо → preview → trial/login → оплата → аудит → письмо → отчёт/экспорт → кабинет. Проверить одну live-заявку каждого рынка и все заявленные AI; зафиксировать решение о выпуске.

## 15. Известные зоны внимания на старте

Это цели тестов, не утверждение о подтверждённых дефектах во всех случаях:

- Исправление футера F-5 пока нужно подтвердить на опубликованном worker и в реально пришедшем BY-письме.
- В cold/research nurture и monitoring alerts есть фиксированные RU-домены/defaults — проверить весь BY-путь.
- YandexGPT/Alisa переведены на релей, успешность после перехода не подтверждена текущей проверкой; GigaChat не настроен.
- Freemium F-4 обещает удаление через 48 часов; F-5 приходит позже. Проверить реальное хранение и согласованность текста.
- В контактном письме обещаны 3–5 минут: измерить реальные сроки и поведение при отсутствии сайта/сбое постановки задачи.
- Повторное использование скана одного сайта несколькими email требует отдельной проверки владельца, opt-out и дублей.
- Алерты сейчас группируют по email: проверить несколько брендов и RU/BY у одного клиента.
- Trial-письмо со скидкой требует фактически работающей скидки и срока, а не только текста.
- Старые TODO/vault статусы местами расходятся с кодом; отчёт о тестировании строить по фактическим результатам.

## 16. Итоговый отчёт проверки

Для решения о релизе подготовить: количество PASS/FAIL/BLOCKED по приоритетам и рынкам; список открытых дефектов с воспроизведением; таблицу реальных AI-ответов; таблицу фактических доставок всех писем; результаты каждой цепочки и FLOW-01…12; отчёты/экспорты по тарифам; платежи и подписки; измеренные сроки/стоимость; непроверенные долгие сценарии; версии web/worker/лендингов и план отката.

Нельзя обозначать «всё протестировано», если есть незавершённые цепочки, пропущенные рынки, неподключённые обещанные платформы или только проверки с mocks.
